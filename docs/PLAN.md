# แผนการทำงานสำหรับ AI Agent
## ระบบหลังบ้านร้านสปา / นวด / เสริมความงาม — "Lotus Desk"

**Stack:** NestJS + Next.js (App Router) + PostgreSQL + Prisma + Tailwind/shadcn
**เอกสารนี้ใช้กับ:** Claude Code, Cursor, หรือ AI coding agent ตัวใดก็ได้ที่รันคำสั่งในเครื่องได้

---

## 0. วิธีใช้เอกสารนี้

เอกสารนี้ออกแบบให้ **1 งาน (Task) = 1 เซสชันของ AI** งานถูกซอยให้เล็กพอที่ AI จะทำจบได้ในเซสชันเดียวโดยไม่หลุด context และมีเกณฑ์ตรวจรับที่วัดได้จริง

**ขั้นตอนตั้งต้น**

1. สร้าง repo เปล่า วางไฟล์นี้ไว้ที่ `docs/PLAN.md`
2. คัดลอกเนื้อหาในหัวข้อ 4 ไปไว้ที่ `CLAUDE.md` (หรือ `AGENTS.md`) ที่ราก repo
3. คัดลอกหัวข้อ 3 (Design System) ไปไว้ที่ `docs/DESIGN.md`
4. เริ่มสั่งงานทีละ Task ตามลำดับในหัวข้อ 5 ด้วยเทมเพลตในหัวข้อ 7

**กติกาที่ต้องยึด**

- ห้ามข้ามลำดับ Task ที่มี dependency ค้างอยู่
- ห้ามสั่ง "ทำ M4 ทั้งหมด" ในครั้งเดียว — AI จะเขียนโค้ดกว้างและตื้น
- ทุก Task ต้องจบด้วย `pnpm verify` ผ่าน + commit 1 ครั้ง
- ถ้า AI ถามคำถามที่เอกสารนี้ตอบไว้แล้ว ให้ชี้กลับไปที่หัวข้อนั้นแทนการตอบใหม่ (กัน decision drift)

## 1. การตัดสินใจที่ล็อกแล้ว (ห้าม AI เปลี่ยนเอง)

ล็อกไว้เพื่อไม่ให้ AI เลือกไลบรารีใหม่กลางทางจนโค้ดสองส่วนเข้ากันไม่ได้

| หัวข้อ | ตัวเลือกที่ล็อก | เหตุผล |
|---|---|---|
| Monorepo | pnpm workspace + Turborepo | แชร์ type ระหว่าง API กับ Web ได้จริง |
| Backend | NestJS 11 (Express adapter) | โครงสร้าง module ชัด AI เขียนตามแบบแผนได้ง่าย |
| ORM | Prisma | schema เดียวอ่านง่าย, migration ปลอดภัย, AI ทำงานกับ Prisma แม่นกว่า TypeORM |
| DB | PostgreSQL 16+ | ต้องใช้ `btree_gist`, `pg_trgm`, `tstzrange` |
| Frontend | Next.js 15 App Router + React 19 | Server Component ลด JS ที่ส่งลงแท็บเล็ตหน้าร้าน |
| Data fetching | TanStack Query v5 (client) + Server Actions (mutation ง่ายๆ) | — |
| UI | Tailwind CSS v4 + shadcn/ui (คัดลอกเข้า repo) | ปรับ token ได้ 100% ไม่ติด lock-in |
| Validation | Zod — schema เดียวใช้ทั้ง API DTO และ React Hook Form | ความจริงเดียว |
| API contract | REST + OpenAPI (`@nestjs/swagger`) → generate client ด้วย `openapi-typescript` | — |
| Auth | JWT ใน httpOnly cookie (access 15 น. / refresh 30 ว.) + PIN login สำหรับเครื่องหน้าร้าน | — |
| Authorization | CASL + `@RequirePermission()` decorator | เงื่อนไขซับซ้อน (เห็นเฉพาะสาขาตัวเอง) ทำได้ |
| Background job | BullMQ + Redis | สรุปรายงานรายวัน, ส่ง LINE, คำนวณค่ามือ |
| Test | Vitest (unit) + Supertest + Testcontainers (integration) + Playwright (e2e) | — |
| Log | pino (JSON) + request-id | — |
| Money | เก็บเป็น **integer สตางค์** (`Int`) ห้ามใช้ float เด็ดขาด | — |
| Time | เก็บ `timestamptz` UTC, แสดงผล `Asia/Bangkok` | — |

**ห้ามทำ:** GraphQL, microservices, Redux, CSS-in-JS runtime, ORM อื่น, การเก็บเงินเป็น `Float`

## 3. Design System — "Celadon & Indigo"

### 3.1 ทิศทาง

โจทย์จริงของหน้าจอนี้คือ **พนักงานต้อนรับที่ต้องจัดคิวให้ถูกภายใน 10 วินาที ขณะที่ลูกค้ายืนรออยู่ตรงหน้า** ไม่ใช่หน้าเว็บขายของสปา ความสวยจึงต้องมาจากความสงบ ความคมของข้อมูล และการอ่านสถานะได้ในพริบตา — ไม่ใช่ภาพดอกไม้กับตัวอักษร serif

**เลือกอย่างจงใจ:** พื้นขาวอมเขียวเย็น + ตัวอักษรน้ำเงินหมึก + **สีเขียวศิลาดล** (celadon เครื่องปั้นดินเผาไทย) เป็นสีหลัก
**หลีกเลี่ยงอย่างจงใจ:** พื้นครีมอุ่น + serif + ส้มดินเผา ซึ่งเป็นภาพจำสำเร็จรูปของคำว่า "สปา" และทำให้หน้าจอดูจ้าเมื่อใช้งานต่อเนื่อง 10 ชั่วโมง

**Signature element:** *Lane Board* — กระดานคิวแนวนอน 1 แถว = 1 พนักงาน มี "รางคิวหมุน" อยู่ริมซ้ายและเส้นเวลาปัจจุบันสีทองเหลืองพาดทั้งจอ นี่คือหน้าจอที่ทั้งระบบถูกจดจำ ให้ลงแรงกับมันมากที่สุดและให้ที่เหลือเงียบ

### 3.5 Layout & density

- Sidebar 240px (ยุบเหลือ 64px ได้) + Topbar 56px มีตัวเลือกสาขาและช่องค้นหาสากล (`Cmd/Ctrl+K`)
- Content max-width 1440px ยกเว้น Lane Board ที่กินเต็มจอ
- ตาราง: แถวสูง 40px โหมดปกติ / 32px โหมดแน่น (จำค่าไว้ต่อผู้ใช้)
- Spacing scale: 4 · 8 · 12 · 16 · 24 · 32 · 48
- **ห้ามใช้ modal ซ้อน modal** — ฟอร์มยาวให้ใช้ Sheet เลื่อนจากขวา
- เงา: ใช้เส้นขอบ 1px เป็นหลัก ใช้เงาเฉพาะ popover / dropdown / dialog

### 3.6 Motion

`--ease: cubic-bezier(.2,.8,.2,1)` ระยะ 120–180ms เท่านั้น

ใช้แค่ 4 ที่: บล็อกนัดตอนลาก, Sheet เลื่อนเข้า, Toast, และชีพจรจางบน spine ของงานที่กำลังบริการ
เคารพ `prefers-reduced-motion` ปิดทั้งหมด

### 3.7 คุณภาพขั้นต่ำ (ตรวจทุก PR ที่แตะ UI)

- โฟกัสคีย์บอร์ดมองเห็นชัด (`outline: 2px solid var(--celadon); outline-offset: 2px`)
- คอนทราสต์ผ่าน WCAG AA (ตัวอักษรปกติ ≥ 4.5:1)
- ทุกหน้าจอทำงานได้เต็มรูปแบบด้วยคีย์บอร์ดล้วน — พนักงานต้อนรับพิมพ์เร็วกว่าจิ้มเมาส์
- ทุกตารางมี empty state ที่บอกว่า "ทำอะไรต่อ" ไม่ใช่แค่ "ไม่พบข้อมูล"
- ข้อความ error บอกสาเหตุ + วิธีแก้ ห้ามขึ้นแค่ "เกิดข้อผิดพลาด"
- ปุ่มที่ทำให้ข้อมูลหาย/เงินเปลี่ยน ต้องใช้สี `--rose` และมีขั้นยืนยัน

### 3.8 การเขียนข้อความ (Copy)

- ใช้คำที่พนักงานพูดจริง: "ตัดคอร์ส" ไม่ใช่ "หักยอด package balance", "คิวหมุน" ไม่ใช่ "rotation assignment"
- ปุ่มบอกสิ่งที่จะเกิดขึ้น: "บันทึกการจอง" ไม่ใช่ "ตกลง"
- ชื่อ action ต้องเหมือนกันตลอดเส้นทาง: ปุ่ม "ปิดบิล" → toast "ปิดบิลแล้ว"
- ตัวเลขเงินแสดง `฿1,250` (ไม่มีทศนิยมถ้าลงตัว) เวลาแบบ 24 ชม. `14:30`

## 4. กติกาสำหรับ AI — คัดลอกไปไว้ที่ `CLAUDE.md`

```markdown
# กติกาการทำงานใน repo นี้

## บริบท
ระบบหลังบ้านร้านสปา/นวด ผู้ใช้คือพนักงานต้อนรับ ผู้จัดการสาขา และเจ้าของร้าน
เอกสารที่ต้องอ่านก่อนเริ่มงาน: docs/PLAN.md, docs/DESIGN.md, docs/DOMAIN.md

## ขอบเขตงาน
- ทำเฉพาะ Task ที่ได้รับมอบหมาย ห้ามทำ Task ถัดไปล่วงหน้า
- ห้ามแก้ไฟล์นอกขอบเขตที่ Task ระบุ ถ้าจำเป็นต้องแก้ ให้หยุดแล้วอธิบายเหตุผลก่อน
- ห้ามเพิ่ม dependency ใหม่โดยไม่ถาม
- ห้ามเปลี่ยนการตัดสินใจในหัวข้อ 1 ของ PLAN.md

## กฎเหล็กด้านโค้ด
1. `packages/core` เป็น pure function เท่านั้น — ห้าม import Prisma, Nest, React, fetch, Date.now()
   (เวลาปัจจุบันให้รับเป็น parameter เสมอ เพื่อให้ test ได้)
2. เงินเก็บเป็น integer หน่วยสตางค์ ตั้งชื่อฟิลด์ลงท้าย `Satang` เช่น `priceSatang`
   ห้ามใช้ Float หรือ parseFloat กับเงินทุกกรณี
3. เวลาเก็บเป็น timestamptz UTC แปลงเป็น Asia/Bangkok เฉพาะตอนแสดงผล
4. ห้ามใช้ `any` และห้าม `@ts-ignore` — ถ้าติดจริงให้หยุดแล้วถาม
5. ทุก query ที่แตะข้อมูลร้าน ต้องกรองด้วย branchId เสมอ ใช้ Prisma extension ที่มีอยู่แล้ว
   ห้ามเขียน raw query ที่ข้าม branch scope
6. ทุก mutation ต้องผ่าน AuditInterceptor — ห้ามเขียน service ที่เลี่ยง
7. ยอดคงเหลือของคอร์ส ห้าม UPDATE ตรง ต้อง INSERT ลง ledger แล้วอ่านผลรวม
8. Schema ที่ใช้ทั้งสองฝั่งต้องอยู่ใน packages/contracts เท่านั้น ห้าม copy type ข้ามแอป
9. UI ใช้ token จาก packages/ui เท่านั้น ห้ามเขียนค่า hex หรือ px ดิบใน component

## กฎเหล็กด้าน UI
- ใช้เฉพาะ CSS variable ที่ประกาศใน docs/DESIGN.md ห้ามสร้างสีใหม่
- ทุกหน้าต้องมี 4 สถานะ: loading (skeleton), empty (พร้อมคำแนะนำว่าทำอะไรต่อ), error (บอกวิธีแก้), success
- ข้อความ UI เป็นภาษาไทยทั้งหมด ใช้คำที่พนักงานร้านพูดจริง
- ทุก interactive element ต้องเข้าถึงด้วยคีย์บอร์ดได้

## ทุก Task ต้องจบด้วย
1. `pnpm verify` ผ่าน (lint + typecheck + test + build)
2. Unit test ครอบ business logic ใหม่ทุกเส้นทาง รวมเคสพัง
3. ถ้าแก้ Prisma schema → สร้าง migration + อัปเดต seed ให้ยังรันได้
4. ถ้าตัดสินใจอะไรที่ไม่มีใน PLAN.md → เขียนเพิ่มใน docs/decisions.md
5. commit เดียว รูปแบบ: `feat(booking): ...` / `fix(core): ...` พร้อมรหัส Task ในบรรทัดแรก

## เมื่อไม่แน่ใจ
หยุด แล้วถามพร้อมเสนอทางเลือก 2–3 ทางและข้อดีข้อเสีย
อย่าเดาแล้วเขียนต่อ — การเดาผิดในโดเมนนี้ทำให้เงินคลาดเคลื่อนจริง
```

## 5. แผนงาน — Milestone และ Task

สัญลักษณ์: **★** = งานที่มีความเสี่ยงสูง ควรตรวจโค้ดด้วยตาเองก่อน merge

### M0 — วางฐาน (ประมาณ 5 Task)

| Task | งาน | เกณฑ์ผ่าน |
|---|---|---|
| **T0.1** | สร้าง monorepo: pnpm workspace, Turborepo, tsconfig base, ESLint+Prettier, สร้าง `apps/api` (Nest) `apps/web` (Next) และ package เปล่าตามโครงสร้างหัวข้อ 2 | `pnpm dev` ยกทั้งสองแอปได้, `pnpm verify` ผ่าน |
| **T0.2** | `docker-compose.dev.yml`: postgres 16 (เปิด `btree_gist`, `pg_trgm`), redis, mailpit + `.env.example` + validate env ด้วย Zod ตอน boot | `docker compose up` แล้วแอปต่อ DB ได้, ถ้า env ขาดต้อง fail ทันทีพร้อมบอกชื่อตัวแปร |
| **T0.3** | ติดตั้ง Prisma ใน `packages/db` + สร้าง enum และ base model (`Branch`, `AuditLog`) + สคริปต์ `db:migrate` `db:seed` `db:reset` | migrate + seed รันได้จากศูนย์ |
| **T0.4** | GitHub Actions: lint → typecheck → test → build, มี postgres service สำหรับ integration test | CI เขียวบน PR เปล่า |
| **T0.5** ★ | สร้าง `packages/ui`: tokens.css (จากหัวข้อ 3.2), Tailwind v4 preset ที่ map token, โหลดฟอนต์ 3 ตัว, ติดตั้ง shadcn/ui, ทำ AppShell (Sidebar + Topbar + ตัวสลับสาขา + ตัวสลับ light/dark) และหน้า Style Guide ที่ `/dev/styleguide` แสดง token, ปุ่ม, ฟอร์ม, ตาราง, badge สถานะทั้ง 7 | เปิด `/dev/styleguide` เห็นครบ, สลับ dark ได้, คอนทราสต์ผ่าน AA ทุกคู่สี |

> T0.5 คือจุดที่กำหนดหน้าตาทั้งระบบ **อย่าปล่อยผ่าน** ถ้ายังไม่พอใจ ให้แก้ที่นี่ก่อนเขียนหน้าอื่น เพราะแก้ทีหลังต้องไล่ทุกหน้า

### M1 — ตัวตน สิทธิ์ และร่องรอย (6 Task)

| Task | งาน | เกณฑ์ผ่าน |

| **T1.2** ★ | Auth: login อีเมล+รหัสผ่าน (argon2), JWT access/refresh ใน httpOnly cookie, refresh rotation + reuse detection, logout ทุกอุปกรณ์ | integration test ครอบ: login สำเร็จ/ผิด, refresh, ใช้ refresh ซ้ำต้องถูกเพิกถอนทั้งสาย |
| **T1.3** | PIN login สำหรับเครื่องหน้าร้าน: อุปกรณ์ผูกกับสาขา, พนักงานกด PIN 6 หลัก, session สั้น 8 ชม., rate limit + ล็อกเมื่อผิด 5 ครั้ง | ทดสอบล็อกและปลดล็อกได้ |
| **T1.4** ★ | RBAC ด้วย CASL + `@RequirePermission()` + Prisma extension บังคับ `branchId` อัตโนมัติทุก query | test: ผู้จัดการสาขา A เรียกข้อมูลสาขา B ต้องได้ 403 ทุก endpoint |
| **T1.5** ★ | Audit log: interceptor เก็บ actor, action, entity, ค่าเดิม, ค่าใหม่, IP, requestId แบบ append-only (revoke สิทธิ์ UPDATE/DELETE ที่ระดับ DB role) | แก้ราคาแล้วมี log พร้อม diff, ลอง UPDATE ตาราง log ตรงๆ ต้องถูกปฏิเสธ |
| **T1.6** | Frontend: หน้า login, middleware ป้องกัน route, ดึงสิทธิ์มาซ่อน/แสดงเมนู, หน้า 403 ที่บอกว่าต้องขอสิทธิ์จากใคร | e2e: login → เห็นเมนูตามบทบาท → logout |

โมดูลที่ยากที่สุด **อ่าน `docs/DOMAIN.md` ให้จบก่อนเริ่ม** และให้ AI ทำทีละ Task โดยเด็ดขาด

| Task | งาน | เกณฑ์ผ่าน |
|---|---|---|
| **T4.1** | `packages/core/availability` — pure function: รับ (กะ, วันลา, นัดที่มีอยู่, ห้อง, บริการ, buffer, เวลาปัจจุบัน) คืนช่วงเวลาที่จองได้ | unit test ≥ 25 เคส: ชนหัว/ชนท้าย/คร่อม/พอดีเป๊ะ/นอกกะ/buffer ทับ/ข้ามเที่ยงคืน/พนักงานไม่มีทักษะ/ห้องผิดประเภท |
| **T4.2** | Schema + constraint: `Appointment`, `AppointmentItem` พร้อม `EXCLUDE USING gist` กันซ้อนทั้งพนักงานและห้อง | ยิงจองพร้อมกัน 50 request ช่องเดียวกัน ต้องสำเร็จ 1 เท่านั้น |

### 7.2 ตัวอย่างคำสั่งเต็มสำหรับ T4.1 (Availability Engine)

```
ทำ Task T4.1 เท่านั้น

สร้าง packages/core/availability เป็น pure function ห้าม import Prisma, Nest, หรือ
เรียก Date.now() — เวลาปัจจุบันรับเป็น parameter

Signature:
  findAvailableSlots(input: {
    now: Date
    date: Date
    shifts: StaffShift[]        // กะของพนักงานวันนั้น
    leaves: StaffLeave[]
    existing: BookedBlock[]     // นัดที่มีอยู่ (มี staffId, roomId, start, end)
    staff: StaffProfile[]       // มี skills[], level
    rooms: Room[]               // มี roomTypeId, capacity
    service: ServiceVariant     // มี durationMin, bufferBeforeMin, bufferAfterMin,
                                //    requiredSkill, requiredRoomTypeId
    granularityMin: number      // 15 หรือ 30
    preferredStaffId?: string
  }): AvailableSlot[]

กติกาที่ต้องบังคับ:
- ช่วงเวลาต้องอยู่ในกะทั้งหมด ไม่คร่อมออกนอกกะแม้แต่นาทีเดียว
- buffer ก่อน/หลังต้องว่างด้วย และ buffer ของงานสองงานทับกันไม่ได้
- พนักงานต้องมี requiredSkill
- ห้องต้องตรง requiredRoomTypeId และยังมี capacity เหลือ
- ต้องว่างพร้อมกันทั้งพนักงานและห้อง
- ไม่คืนช่วงเวลาที่เริ่มก่อน now
- ถ้าระบุ preferredStaffId ให้คืนเฉพาะคนนั้น

เขียน unit test ด้วย Vitest อย่างน้อย 25 เคส ต้องมีอย่างน้อยนี้:
ชนหัว / ชนท้าย / คร่อมทั้งงาน / จบพอดีกับที่อีกงานเริ่ม (ต้องจองได้ถ้าไม่มี buffer)
/ buffer ทับกัน / นอกกะ / คร่อมขอบกะ / วันลา / กะแบ่งครึ่ง (พักเที่ยง)
/ พนักงานไม่มีทักษะ / ห้องผิดประเภท / ห้องเต็ม capacity / ไม่มีห้องว่างแต่คนว่าง
/ ไม่มีคนว่างแต่ห้องว่าง / เวลาผ่านไปแล้ว / granularity 15 vs 30
/ ข้ามเที่ยงคืน (ร้านปิด 02:00) / DST ไม่เกี่ยวเพราะไทยไม่มี แต่ต้องทดสอบ timezone offset

ห้ามเขียนอะไรนอกเหนือจาก packages/core/availability และ test ของมัน
```

## 8. `docs/DOMAIN.md` — คำถามที่คุณต้องตอบก่อนเริ่ม M4

AI ตอบคำถามพวกนี้แทนไม่ได้ เพราะแต่ละร้านกติกาไม่เหมือนกัน **ถ้าไม่ตอบ AI จะเดา และจะเดาผิด** ตอบเป็นข้อความสั้นๆ ใส่ไฟล์นี้ก่อนเริ่ม

**คิวและการจ่ายงาน**
1. คิวหมุนเรียงตามอะไร — เวลามาถึง หรือ จำนวนชั่วโมงสะสมวันนี้ (คนทำน้อยได้คิวก่อน)?
2. พนักงานที่ถูก "ลูกค้าขอ" เสียตำแหน่งคิวหมุนหรือไม่?
3. งานที่ลูกค้ายกเลิกกะทันหัน พนักงานได้กลับต้นคิวหรือท้ายคิว?
4. รับจองล่วงหน้าได้กี่วัน? ยกเลิกฟรีได้ถึงกี่ชั่วโมงก่อนนัด?

**คอร์ส**
5. คอร์สหมดอายุแล้วยังใช้ได้ไหม (ใช้ได้แต่ต้องผู้จัดการอนุมัติ / ใช้ไม่ได้เลย)?
6. โอนคอร์สให้คนอื่นได้ไหม? โอนได้บางส่วนหรือทั้งคอร์ส?
7. คืนเงินคอร์สที่ใช้ไปบางส่วนคิดอย่างไร — หักตามราคาเต็มของครั้งที่ใช้ หรือตามสัดส่วน?
8. แช่แข็งคอร์สได้กี่วันต่อปี ต้องใครอนุมัติ?

**ค่ามือ**
9. โครงสร้างค่ามือปัจจุบันคืออะไร — ขอ **ตารางจริง** ทุกบริการ ทุกระดับพนักงาน ทั้งกรณีคิวหมุนและลูกค้าขอ
10. ตัดคอร์สคิดค่ามือจากอะไร — มูลค่าหน้าบัตร ราคาขายจริง หรือเรตคงที่?
11. ขายคอร์สได้คอมมิชชั่นเท่าไร ใครได้ — คนขาย คนนวด หรือแบ่งกัน?
12. ทิปเข้าใครทั้งหมด หรือหักเข้าร้านบางส่วน?
13. มีค่าปรับสาย/ขาดงานไหม หักอย่างไร?

**ส่วนลดและการอนุมัติ**
14. แคชเชียร์ให้ส่วนลดเองได้กี่ % เกินนั้นใครอนุมัติ?
15. โปรโมชั่นซ้อนกันได้ไหม ถ้าได้ ลำดับการคำนวณเป็นอย่างไร?
16. ยกเลิกบิลหลังปิดรอบกะแล้ว ทำอย่างไร?

**ภาษีและบัญชี**
17. ร้านจด VAT ไหม? ต้องออกใบกำกับภาษีเต็มรูปหรือไม่?
18. รับรู้รายได้จากคอร์สตอนขาย หรือตอนลูกค้าใช้บริการ? (ทางบัญชีคือตอนใช้ — ยืนยันกับผู้ทำบัญชี)
